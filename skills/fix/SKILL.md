# /fix — 원인을 증거로 찾고, 다른 모델의 반박을 거쳐, 딱 정리해서 묻고, 고친다

## 0. 드라이버와 검토자

드라이버는 지금 이 스킬을 읽는 에이전트다. 진단과 수정은 **항상 다른 모델**이 반박 검토한다.

| 드라이버 | 기본 검토자 | 호출 (읽기 전용, 결과는 JSON 한 줄 `{"sessionId","text"}` + 실패 시 `"error"`) |
|---|---|---|
| Claude (Claude Code) | Sol, 엄격 등급이면 Astra | Sol: `bash ~/.claude/skills/team/sol-turn.sh <요청파일> [new\|<sessionId>]`<br>Astra: 앞에 `SOL_MODEL=gpt-6-astra` |
| Astra (Codex, gpt-6-astra) | Claude Opus | `bash ~/.claude/skills/fix/claude-turn.sh <요청파일> [new\|<sessionId>]` |
| Sol (Codex, gpt-6.1-sol) | Claude Opus | 위와 같음 |

- **엄격 등급**: 결제, 인증·권한, 운영 데이터 보정, 스키마·migration, 개인정보가 걸린 이슈. Astra는 비싼
  검토자라 이때와 사용자가 지정할 때만 쓴다. 1단계에서 등급을 정하고 진단 보고에 적는다.
- 요청에 `--reviewer astra|sol|claude|none`이 있으면 따른다. 드라이버와 같은 모델은 검토자로 쓰지 않는다.
  `none`이면 보고에 "교차 검토 없음"이라고 적는다.
- 두 스크립트 모두 읽기 전용이다. Codex 검토자는 OS sandbox가 쓰기를 막고, Claude 검토자는 권한 설정이
  쓰기와 git 변경을 거부한다. 검토자는 운영 로그·DB에 접근하지 않는다. 드라이버가 모은 증거 파일과
  저장소만 본다. 더 필요한 데이터는 검토자가 "확인이 필요한 것"으로 요청하고, 드라이버가 조회한다.
- 다음 라운드는 같은 `sessionId`로 재개한다(검토자가 앞 라운드를 기억한다). 진단 검토와 수정 검토도 같은
  세션을 이어 쓴다.
- 기다리는 법: Claude Code는 Bash `run_in_background: true`, `timeout: 3600000`으로 실행하고 알림을
  기다린다. Codex는 그대로 실행하고 끝날 때까지 기다린다. 검토 한 번에 수 분 걸린다.

## 공통 규칙

- **전역 규칙이 우선한다.** 조사 소스와 금지 사항은 전역 `AGENTS.md`의 3절(읽기 전용 조사 소스),
  6절(운영 데이터), 7절(프로젝트 라우팅), 8절(민감 파일)을 따른다. 프로젝트 정본이 있으면 연다.
  도메인 전용 조사 스킬이 있으면 2단계 안에서 그 절차를 따른다(예: PhoneGo 결제·계약·동기화·캐시 →
  `phonego-incident-analysis`).
- **확인과 추론을 섞지 않는다.** 모든 주장에 근거를 붙인다: `file:line`, 로그 시각과 쿼리, CI run ID,
  쿼리 결과 건수. 근거 없는 것은 "추론" 또는 `not verified: <이유>`로 표시한다. 고객 이름·연락처·
  주소·결제정보·토큰·원본 payload는 보고에 넣지 않는다(내부 ID만).
- **사용자를 부르는 곳은 정해져 있다.** 진단 게이트(4단계), 데이터 보정 승인(7단계), 그리고
  사용자만 풀 수 있는 막힘(예: AWS SSO 만료 → `aws sso login --sso-session phonego` 부탁)뿐이다.
  막혀도 나머지 소스로 계속한다. 그 밖에는 끝까지 진행하고 한 번에 보고한다.
- **끝까지 모드**: 요청에 "끝까지", "멈추지 말고", "가이드대로"가 있으면 진단 게이트에서 멈추지 않는다.
  그때도 멈추는 곳은 운영 데이터 쓰기, 제품 동작이 갈리는 선택(방안마다 사용자가 보는 결과가 다름),
  사용자만 풀 수 있는 막힘뿐이다. 멈추지 않았으면 진단 보고를 결과 보고 앞에 같이 붙인다.
- **작업 파일**은 `/tmp/fix/<slug>/`에 둔다(`evidence.md`, 검토 요청·응답, diff). `<slug>`는 짧은
  kebab-case.
- commit·push·PR·배포·운영 write·migration 실행은 전역 규칙대로 사용자가 명시적으로 요청할 때만 한다.
- 모든 사용자 출력은 사용자가 쓰는 언어로 한다.

## 1. 접수 (짧게)

- 증상을 시스템 위치로 옮긴다: 어느 화면·API·배치에서, 누가, 언제부터, 기대한 것과 실제, 얼마나 자주.
  메시지 문장을 다시 풀지 말고 실제 코드·데이터의 어느 부분인지로 바꾼다(전역 4절).
- 분류: 코드 버그 / 데이터 이상 / 설정·인프라 / 외부 연동 / CI. 심각도: 고객 영향, 돈, 데이터 손실,
  지금도 발생 중인지. 등급: 엄격(0절) / 일반.
- 요청에 사용자가 의심한 원인이 있으면 적어 둔다. 진단 보고에서 하나하나 원인인지 예/아니오로 답한다.
- 계정·주문·시각처럼 로그·DB에서 찾을 수 있는 것은 묻지 않고 찾는다. 가진 소스를 다 써도 답이 없어
  진행할 수 없는 정보만 묻는다(4단계의 질문 형식).

## 2. 증거 수집 (읽기 전용)

순서: 관찰·재현 → 코드 경로 → 언제부터 → 로그·지표 → 데이터.
- **코드**: 증상 지점에서 실제 흐름을 끝까지 따라간다. 중간을 추측으로 건너뛰지 않는다.
- **언제부터**: `git log -S`/`--since`/`blame`, 관련 PR, 배포 run(`gh run list/view`). 증상 시작 시각과
  배포 시각을 맞춰 본다.
- **로그·지표**: Grafana MCP(Loki·Prometheus·Tempo), AWS CloudWatch·EKS 읽기 명령(전역 3절).
- **데이터**: 전역 6절 경로로 읽기 전용. 건수, 기간, 대표 내부 ID 위주로 본다.
- **재현**: 가능하면 로컬에서 실패하는 테스트로 재현한다. 이 테스트가 5단계의 회귀 테스트가 된다.
- 모은 것은 바로바로 `/tmp/fix/<slug>/evidence.md`에 적는다. 항목마다 `[확인]`/`[추론]`, 출처(명령,
  쿼리, run ID, 시각).
- 가설은 2~3개까지 세운다. 각각 지지 증거와 반증 증거를 적고, 반증되면 지운다.
- **조사의 끝**: 횟수나 시간이 아니라, 아래 네 가지에 증거로 답했을 때 진단 초안을 쓴다. 접속 불가·
  권한 없음처럼 확인할 수 없는 것만 "확인하지 못한 것"에 이유와 함께 남긴다.
  1. 이번 사례: 정확히 무엇이(내부 ID), 언제, 어떻게 됐나.
  2. 원인: 처음 잘못된 상태와 그 상태를 만든 경로까지 거슬러 올라간다. "이 조건이면 막힌다"는 차단
     조건이지 원인이 아니다.
  3. 의심한 것: 사용자가 의심한 원인마다 예/아니오와 근거.
  4. 고치는 법: 이번 사례 복구와 재발 방지, 각각의 크기와 위험.

## 3. 교차 진단 검토 (필수, 최대 2라운드)

1. 요청 파일 `/tmp/fix/<slug>/diagnosis-req.md`를 쓴다: 저장소 경로, 증상, 진단 초안(원인·근거·영향
   범위·수정 방안), `evidence.md`의 절대경로, 관련 파일 경로, 그리고 아래 지시와 형식.
   ```
   너는 이 진단을 깨뜨리려는 검토자다. 동의하려 하지 말고 틀린 곳을 찾아라.
   읽기 전용: 파일을 쓰지 말고 읽기 명령만 실행하라. 증거 파일과 저장소 코드를 직접 확인하고
   모든 지적에 근거(file:line, 증거 파일의 항목)를 붙여라. 추측은 추측이라고 써라.
   요청(증상)에 없는 것은 요구하지 말고, 진단·수정 방안이 근거 없이 더한 것을 지적하라.
   ## 동의
   ## 반박 (근거 필수)
   ## 놓친 가능성 (다른 원인 후보, 영향 범위 누락)
   ## 확인이 필요한 것 (드라이버가 조회해야 할 로그·쿼리·파일 — 구체적으로)
   ## 수정 방안 의견 (더 작은 수정, 회귀 위험)
   ## Verdict: 원인 확정 | 조건부 확정 (조건) | 원인 불충분
   사용자의 언어로 답하라.
   ```
2. 0절의 검토자를 `new`로 호출한다. 응답을 `/tmp/fix/<slug>/diagnosis-<검토자>-1.md`에 저장한다.
3. **항목마다 직접 확인한다.** 맞으면 수용(진단 수정), 틀리면 근거를 들어 반박한다. "확인이 필요한 것"은
   실제로 조회해서 `evidence.md`에 추가한다. 검토자의 말을 권위로 받아들이지 않는다.
4. 이견이 남았거나 판정이 바뀔 만한 새 증거가 있으면 2라운드: 같은 `sessionId`로 수용/반박/새 증거만
   짧게 보낸다.
5. 검토자가 오류를 내거나 `## Verdict:`가 없으면 같은 세션으로 한 번 다시 요청한다("필요한 형식으로
   지금 답하라"). 그래도 실패하면 4단계 보고에 "교차 검토 실패"라고 쓴다. "문제없음"으로 읽지 않는다.

## 4. 진단 게이트 — 여기서 멈춘다

아래 형식 그대로, 짧게 보고하고 **턴을 끝내 답을 기다린다**. 예외는 끝까지 모드(공통 규칙)뿐이다.

```
## 진단: <한 줄 결론>
확신도: 높음 | 중간 | 낮음 — <이유 한 줄>
등급: 엄격 | 일반 — <엄격이면 이유>

### 의심하신 것      ← 사용자가 원인을 의심했을 때만
- <의심한 요인>: 원인 맞음 | 원인 아님 | 일부 — <근거 한 줄>

### 현상
- 무엇이, 어디서, 언제부터, 얼마나 (확인된 숫자)

### 원인
- <원인> — 근거: `file:line`, 로그 <시각·쿼리>, 데이터 <건수>
- 흐름: A → B → C   (필요할 때만, 3~5단계)

### 영향 범위
- 건수·기간·대상(내부 ID만), 지금도 발생 중인지

### 교차 검토 (<검토자 모델>, N라운드)
- 반영: … / 반박하고 유지: … / 남은 이견: …

### 확인하지 못한 것
- not verified: <무엇> — <이유>

### 수정 방안 (재발 방지)
- A. <방안> — 바뀌는 곳, 위험, 크기  ← 추천
- B. <방안> — …
- 데이터 보정: 필요 없음 | 필요 — <대상 건수와 방법> (실행은 별도 승인)

### 결정해 주세요
1. 수정 — A 방안 A(추천) / B 방안 B / X 진단만 하고 종료
2. 데이터 보정 — A 미리보기 만들기 / B 나중에 / C 안 함      ← 필요할 때만
3. 구현 — A 드라이버가 직접(추천) / B 워커(<모델>)에게      ← 크기상 선택지가 있을 때만
→ "1A 2B"처럼 답해 주세요.
```
- **이 보고를 채팅 답변에 형식 그대로 쓴다.** 요약본이나 파일 링크로 대신하지 않는다. 같은 내용을
  `/tmp/fix/<slug>/diagnosis.md`에도 저장한다(수정·`/team` 인계·결과 보고가 이 파일을 가리킨다).
- 모든 선택지에 기호(A/B/C…)를 붙이고 추천을 표시한다. 사용자는 번호와 기호만으로 답한다.
- 질문은 최대 4개. 각 질문에 선택지와 추천을 붙인다. 답에 따라 결과가 달라지지 않는 질문은 넣지 않는다.
- 요청이 `diagnose`이거나 "왜 이래?"류의 질문이면 1번을 "수정 진행 / 여기서 종료"로 둔다.
- 답이 수정 방안을 바꾸면 진단 파일을 고치고, 바뀐 부분만 다시 보여 준다.

## 5. 수정

- **크기에 따라 나눈다.**
  - 작은 수정(대략 3파일 이하, 스키마·결제·migration이 아님): 드라이버가 직접 고친다. 사용자가 워커를
    골랐거나 "○○한테 시켜"라고 했으면 워커가 한다(전역 2절).
  - 큰 수정, 또는 되돌리기 비싼 결정이 필요한 수정: 진단 파일을 배경으로 `/team`에 넘긴다. Claude
    Code라면 바로 넘긴다. Codex라면 사용자에게 Claude Code에서
    `/team <진단 파일 경로>의 수정 방안 A 구현`을 실행하라고 안내하고 멈춘다.
  - 워커: Orca 안이면 `orchestration` 스킬로 띄운다. UI 작업은 `--agent claude --model sonnet`, 그 외는
    `--agent codex --model gpt-6.1-sol --effort high`. spec에는 진단 파일 경로, 고를 수정 방안, 범위,
    완료 조건, "커밋하지 말 것", 아래 최소 수정 원칙을 넣는다.
  - Sol 워커가 한도·인증·실행 실패로 일을 못 하면 같은 spec으로 Sonnet 워커를 띄우고, 결과 보고에
    "Sol → Sonnet: <이유>"를 적는다. 반대(Sonnet → Sol)로는 바꾸지 않는다.
- **순서**: ① 증상을 재현하는 회귀 테스트를 먼저 쓰고 실패를 확인한다. 테스트로 재현할 수 없으면 이유와
  대신 쓸 검증 방법을 적는다. ② 최소 수정 ③ 회귀 테스트 통과 + 관련 기존 테스트 실행.
- **최소 수정 원칙**: 각 조각마다 순서대로 묻는다. 꼭 필요한가? 이 코드베이스에 이미 있나? 표준
  라이브러리? 플랫폼 기본 기능? 설치된 의존성? 한 줄로 되나? 처음 "예"에서 멈춘다. 신뢰 경계의 검증,
  데이터 손실 처리, 보안, 접근성은 줄이지 않는다.
- 원인과 무관한 리팩터링이나 정리를 하지 않는다. 지나가다 본 다른 문제는 8단계 "따로 볼 것"에 적는다.
  같은 함수의 비슷한 위험이라도 증상·진단에 없는 예방 수정은 하지 않고 "따로 볼 것"에 적는다.

## 6. 수정 검토 (교차 모델, 최대 3라운드)

- `git diff > /tmp/fix/<slug>/fix.diff` 후, 진단 때와 **같은 검토자 세션**을 재개해서 보낸다(진단을
  기억한다). "요청에 없는 것은 요구하지 말고, 근거 없이 더한 것을 지적하라"를 다시 적는다. 형식:
  ```
  ## Verdict: APPROVE | REQUEST_CHANGES
  ## 원인을 실제로 고쳤나 (진단의 원인 문장을 인용해 대조)
  ## 회귀 위험 (근거)
  ## 필수 수정 (file:line, 무엇을 어떻게)
  ## 제안 (선택)
  ```
- **증거가 먼저다.** 드라이버가 회귀 테스트와 관련 테스트를 직접 다시 돌리고 출력(통과·실패 수, exit
  code)으로 판단한다. 워커의 "통과했다"는 주장으로만 받는다.
- Claude Code 드라이버이고 `ponytail:ponytail-review` 스킬이 있으면, Skill 도구로 같은 diff에 돌려
  과설계 항목을 걸러 반영한다(`/ponytail…`을 프롬프트로 치지 않는다).
- REQUEST_CHANGES → 고치고 같은 세션으로 재검토. 3라운드 뒤에도 승인이 안 나면 멈추고 양쪽 근거를
  보고한다.

## 7. 데이터 보정 (필요할 때만)

- 전역 6절 그대로 한다. 허용된 write만, 정확한 before/after 미리보기를 보여 주고 사용자의 직전 승인을
  받는다. 허용 범위 밖이면 SQL이나 스크립트만 작성하고 실행하지 않는다.

## 8. 결과 보고

채팅 답변에 아래 형식 그대로 쓴다(요약본이나 파일 링크로 대신하지 않는다). `/tmp/fix/<slug>/result.md`에도
저장한다.
```
## 수정 완료: <한 줄>
- 보고서: /tmp/fix/<slug>/report.html
- 원인: <한 줄> (진단: /tmp/fix/<slug>/diagnosis.md)
- 수정: <파일 목록> — 구현: <드라이버 | 워커 모델>  (모델을 바꿨으면 "Sol → Sonnet: <이유>")
- 검증: <명령> → <통과 N, 실패 0, exit 0>, 회귀 테스트: <이름>
- 교차 검토: <검토자 모델> N라운드 — 리뷰로 바뀐 것: …
- 데이터 보정: 안 함 | 실행함(N건) | 승인 대기
- 배포 후 확인할 것: <로그 쿼리·지표·데이터 쿼리>
- 따로 볼 것: …
- 남은 일: commit·push·PR·배포는 요청하시면 진행
```

**HTML 보고서** `/tmp/fix/<slug>/report.html`: 한 파일로 끝나게 쓴다(CSS는 `<style>` 안에, 외부 스크립트·
폰트·이미지 링크 없음). 진단(`diagnosis.md`)과 결과(`result.md`)의 내용에 더해, 채팅에는 길어서 뺀 것을
담는다: 근거 표(주장 / 출처 / 확인·추론), 교차 검토 라운드별 수용·반박, 수정 diff 요약, 검증 명령과 출력
끝부분. 사용자가 판단하는 순서(현상 → 원인 → 영향 → 수정 → 검증 → 남은 일)로 놓는다. 고객 개인정보는
채팅과 같은 기준으로 넣지 않는다. 진단만 하고 끝나도 마지막에 같은 형식으로 쓴다.
